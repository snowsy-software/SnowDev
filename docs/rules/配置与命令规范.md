# 配置与命令规范

## 配置

1. 默认且唯一支持的配置文件是项目根目录的 `snowdev.config.mjs`；第二阶段之前不支持 `.ts` 配置。
2. 配置必须默认导出对象，并在执行前通过 schema 校验。
3. `compose.file` 与 `compose.projectName` 必填；每个 profile 必须声明受支持的 `kind` 和至少一个服务。
4. 不接受任意 shell 命令字符串、秘密值或未受控 destructive hook 作为配置能力。
5. `profiles.<name>.health` 可选，声明 HTTP 就绪探针：`url` 必填，`timeoutMs`、`intervalMs` 为可选正整数（默认 60000 / 1000）。
6. `profiles.<name>.host` 描述宿主进程，`kind` 为 `host-app-with-compose-deps` 时必填：`command` 必填，`args` 为字符串数组，`stopGraceSeconds` 为可选正整数（默认 10）。`command` 与 `args` 只作为可执行文件与参数数组使用，永不经 shell 解释。
7. `hooks` 可选，声明具名生命周期回调；仅允许 `beforeRun`、`afterDependenciesReady`、`beforeDown` 三个函数键与 `task` 对象键，出现其他键即校验失败。`task` 的每个值都是函数，且其名字不得与 `tasks.<name>` 重名。hook 必须是函数，不接受 shell 字符串。
8. 每个 `tasks.<name>` 都必须声明 `isolated: true`。任务总是使用独立、可销毁的 Compose project，不能加入正在运行的开发环境。

## Hooks

custom hook 是消费项目在 `snowdev.config.mjs` 中导出的 JavaScript 函数，用于接入初始化、迁移、代码生成等项目专属逻辑，而不必复制 core、也不往配置里塞 shell 字符串。

`snowdev.config.mjs` 是项目维护者提供的受信任代码，不是隔离执行环境；其模块顶层和 hook 函数仍拥有 Node.js 权限。SnowDev 只保证其提供的 `context.exec` 使用参数数组和 `shell: false`，不能将不受信任的配置或第三方 hook 当作安全边界。

1. 具名 hook：`beforeRun`（任何容器或宿主进程启动前）、`afterDependenciesReady`（Compose 依赖健康后、宿主进程启动前）、`beforeDown`（`down` 停止任何东西前）、`hooks.task.<name>`（`snowdev task <name>` 在没有同名 Compose task 时执行的纯 JS 任务）。
2. hook 收到唯一参数 `HookContext`：`{ key, profile?, config, cwd, env, log, exec }`。`env` 已按固定优先级合并；`log(line)` 写入 stderr；`exec(command, args?, options?)` 通过 `shell: false` 的执行器运行可执行文件，只接受参数数组，命令写入可复制日志，返回 `{ exitCode }`。
3. `afterDependenciesReady` 只在后台 `compose-service` 与 `host-app-with-compose-deps` 路径触发；附着式前台 `compose-service` 没有独立的依赖就绪阶段，不触发。`container-cli` 在所有一次性服务成功后触发一次。
4. hook 抛出的任何错误都会被包装为 `E_HOOK_FAILED` 并中止当前命令；`beforeRun` 失败时不会执行任何 Compose 调用。
5. `hooks.task.<name>` 正常返回即视为成功（退出码 0）；需要非零退出时应在 hook 内基于 `exec` 结果自行 `throw`。

## Compose 与进程

1. 进程调用只能传递 executable 与参数数组，固定 `shell: false`。
2. Compose 调用始终显式使用 `docker compose --project-name <base>-<profile> -f <file> --profile <profile>`。一个 profile 一个 project，因此 `down dev` 不会停止 `stag` 或 `prod`。
3. 参数不得经字符串拼接后交给 PowerShell、cmd、bash 或其他 shell 解释。
4. 新增 Compose 子命令必须测试含空格的 project name、服务名或路径参数，保证 Windows/Linux 的参数边界一致。

## 环境优先级

环境变量按从低到高的顺序合并：配置默认值、`.env`、`.env.<profile>`、`.env.local`、`.env.<profile>.local`、当前进程环境。环境加载不执行命令替换、插值或 shell 表达式。

## 命令语义

`run stag` 与 `run prod` 永远不得隐式 `docker compose down`。volume 删除只能由明确的 `reset dev --yes` 触发，且不得允许 staging 或 production 重置。尚未实现的命令必须清晰失败，不能伪装成成功。

已实现的生命周期命令：

- `run <profile>`：按 `kind` 启动。`compose-service` 前台 profile（默认 `dev` 或 `foreground: true`）以 `up` 附着运行；后台 profile 以 `up -d --build` 启动后轮询 `docker compose ps --format json`，直到服务运行且已声明的 healthcheck 为 `healthy`。`host-app-with-compose-deps` 先以 `up -d` 启动依赖并进行相同等待，再启动宿主进程（前台附着，后台写 PID）。可选 HTTP probe 随后等待；两种等待均在超时时提供诊断。`container-cli` 对每个服务执行 `run --rm`。任一路径都不会发出 `down`。启动前触发 `hooks.beforeRun`，依赖就绪后触发 `hooks.afterDependenciesReady`（附着式前台 `compose-service` 除外）。
- `down [profile]`（默认 `dev`）：显式停止。先触发 `hooks.beforeDown`，再对 `host-app-with-compose-deps` 受控停止宿主进程（SIGTERM，宽限期后 SIGKILL），最后 `docker compose down --remove-orphans`。绝不传 `--volumes`。
- `logs [profile]`（默认 `dev`）：默认 `logs -f`；`--no-follow` 只打印一次。
- `ps [profile]`（默认 `dev`）：`docker compose ps`，并附带宿主进程 PID 状态。
- `init [profile]`（默认 `dev`）：首次初始化，创建 `.snowdev/` 并 `up -d --build`。打印影响范围，必须带 `--yes`。
- `init template [kind]`（默认 `compose-service`，另有 `hybrid-host-service`、`container-cli`）：从已安装包的 `templates/<kind>/` 落地 `snowdev.config.mjs`、`docker/compose.yml`、`.env.example`。目标文件已存在即跳过并提示，绝不覆盖；不修改 `package.json` 或已有 Compose 文件。非法 `kind` 抛 `E_INVALID_ARGUMENT`。
- `reset [profile]`（默认 `dev`）：仅允许 `dev`；打印影响范围，必须带 `--yes`；执行 `docker compose down --volumes --remove-orphans`。
- `task <name>`：先读 `config.tasks.<name>`。所有 Compose task 必须为 `isolated: true`，使用 `"<projectName>-task-<name>"` 作为 Compose project 名（与任何 profile 都不同），并在 `finally` 中执行 `down --volumes --remove-orphans`。没有同名 Compose task 时，回退执行 `config.hooks.task.<name>` JS hook；两者都没有才抛 `E_TASK_NOT_FOUND`。

## 运行时状态

宿主进程 PID 记录写入消费项目的 `.snowdev/<projectName>-<profile>.host.json`。该目录由 SnowDev 维护，消费项目应将其加入 `.gitignore`。
